# XDC Architecture

XDC (Xiatian Distributed Compute) is a self-hosted system for **real multi-device training and layer-sharded inference**, not a wrapper that forwards prompts to one machine's model server.

```
                        ┌──────────────────────────────────────────┐
                        │              Coordinator                 │
                        │  FastAPI · TLS · Ed25519 request auth    │
                        │  scheduler · DiLoCo engine · pipeline    │
                        │  durable state · dashboard · /metrics    │
                        └───────┬───────────────┬──────────────────┘
              signed HTTP       │               │     outbound WebSocket RPC
              downloads/uploads │               │     (NAT-friendly relay)
                 ┌──────────────┴─────┐   ┌─────┴──────────────┐
                 │ Worker A (macOS)   │   │ Worker B (Windows) │
                 │ PyTorch CPU/MPS    │   │ PyTorch CPU/CUDA   │
                 │ local AdamW steps  │   │ pipeline stage 1   │
                 │ data shard only    │   │ KV cache local     │
                 └────────────────────┘   └────────────────────┘
```

Only the coordinator needs a reachable port. Workers make outbound connections, which is the practical NAT/firewall model for homes, laptops and offices. Computation is distributed; discovery and round coordination are centralized in v0.1.

## 2. Identity and transport security

1. Each worker creates `data_dir/identity/node_key.pem` (Ed25519, mode 0600).
2. `node_id = "node-" + sha256(public_key)[:24]`.
3. Registration includes public key, capabilities, timestamp, nonce and signature; the coordinator checks `node_id`, join token, skew and replay.
4. Every worker request signs:

   ```
   xdc-v1
   METHOD
   /path?query
   timestamp
   nonce
   sha256(body)
   ```

5. Admin endpoints require a bearer admin token. The dashboard never embeds it.
6. TLS server auth uses a private CA generated by `xdc init`. The worker verifies the CA. Tunnel tokens are stored only as hashes.
7. `X-XDC-Meta` carries update metadata; the body is covered by the signature.
8. Workers download only their assigned data shard and only their own pipeline stage weights.

Not implemented in v0.1: client certificates/mTLS, encrypted data at rest, Byzantine consensus, anonymous public-swarm privacy.

## 3. Training: DiLoCo with a decoupled quorum

### 3.1 Job lifecycle

```
queued → running ⇄ waiting → completed
                    ↘ paused → running
                    ↘ failed
```

- `running`: a round is open or can be opened.
- `waiting`: fewer than `min_workers` online; retried every tick.
- `paused`: in-flight round discarded; last committed weights remain.
- `completed`: all configured rounds committed.
- `failed`: three consecutive round failures or an unrecoverable error.

Coordinator state is atomically persisted (`state.json`). On restart, uncommitted rounds are discarded and running jobs continue from the last committed global weights; paused/failed jobs can be resumed. Optimizer momentum is saved in `outer_optimizer.safetensors`.

### 3.2 Round protocol

```
Coordinator                            Worker i
    │  assignment (base model, shard, H, lr) │
    ├───────────────────────────────────────▶│
    │                                        │ load model + only shard i
    │                                        │ H × AdamW local steps
    │                                        │ delta = local − base
    │        signed safetensors delta        │
    │◀───────────────────────────────────────┤
    │ quorum + grace or deadline             │
    │ robust filter + token-weighted average │
    │ outer momentum update                  │
    │ save checkpoint + evaluate             │
    │ version += 1                           │
```

Key details:

- Shards are contiguous and disjoint; the dataset endpoint slices the file **before** transfer. A worker never receives the whole training split unless its shard is the whole split.
- `compression=fp16` halves the wire payload; the coordinator casts to float32 for aggregation.
- Robust filtering: if ≥3 updates, compute L2 norms, drop non-finite/zero updates and updates above `max_norm_ratio × median`. With two workers there is no meaningful robust median, so only finiteness/shape/absolute ceiling apply.
- Weights are token counts (`local_steps × batch × seq_len`), so heterogeneous workers contribute proportionally.
- `quorum = ceil(expected × quorum_fraction)`, clamped to `[min_workers, expected]`; `algorithm=diloco` requires all expected workers.
- After `quorum` is reached, `grace_s` accepts stragglers. At deadline, the round commits if `submitted >= min_workers`.
- If every expected node has submitted or been declared lost, and at least `min_workers` updates exist, the round commits immediately. This is the consumer-friendly fault-tolerance path.
- Liveness mid-round uses **both** the heartbeat and the actual WebSocket tunnel. A busy laptop can delay its heartbeat loop for tens of seconds while still training; a live tunnel keeps it in the round. If all remaining workers are lost and the round cannot reach `min_workers`, the coordinator waits a bounded recovery window (`2 × heartbeat_timeout`, clamped to 5–30 s) and then retries instead of stalling until the deadline.
- A valid update from a worker that was declared lost is **re-admitted** while the round is still open and the base version matches. This avoids discarding a completed local round after a transient liveness misclassification.
- Late, duplicate or invalid updates are rejected; reputation is reduced for genuinely invalid payloads.
- The coordinator evaluates validation loss on held-out bytes at `eval_every` (CPU by default) and stores metrics/events.

### 3.3 Checkpoints

```
data/jobs/<job_id>/
  init.safetensors
  global.safetensors              # latest committed weights
  outer_optimizer.safetensors     # momentum state
  checkpoints/v00001.safetensors
  job.json                        # model/training/metrics metadata
  updates/<round>/<node>.safetensors
  train.bin, val.bin
```

`checkpoint_keep` bounds old checkpoint retention. `init_checkpoint_job` initializes a new job from another job's latest checkpoint, enabling continued pretraining/SFT workflows.

## 4. Inference: real layer pipeline

### 4.1 Allocation

1. Only nodes with an active tunnel, fresh heartbeat and reputation above the floor are candidates.
2. Candidates are sorted by measured compute score × reputation.
3. Contiguous layers are allocated in proportion to score, with every stage receiving at least one layer and endpoint stages slightly discounted for embedding/head work.
4. Each stage receives a distinct safetensors slice. Workers never receive the whole checkpoint.

Example with 4 layers and two workers:

```
stage 0: tok_emb + pos_emb + blocks[0:2]
stage 1: blocks[2:4] + norm + head
```

### 4.2 Token loop

```
prompt ──▶ stage0 ──hidden──▶ stage1 ──logits──▶ coordinator samples
             ▲                                      │
             └──────── token (KV cache stays) ◀─────┘
```

- Prefill sends the prompt once; decode sends one token per step.
- Each stage owns its KV cache. `PipelineStage.forward` appends K/V tensors locally; the coordinator never stores KV.
- The final stage returns only the last-position logits. Sampling is temperature/top-k, using the C++ sampler when available.
- Raw generated bytes are streamed using SSE `token` events, so partial UTF-8 is preserved.
- Context is limited by `model.block_size`; prompts are truncated from the left and generation is capped at `block_size − 1`.
- `stage_sha256` binds each download; the stage token is short-lived and bound to one node.
- Stage modules are cached by `(sha,start,end)` to reduce repeated time-to-first-token.

### 4.3 Failure and retry

- If a tunnel RPC fails, the node is penalized, excluded, and the pipeline is replanned.
- Non-streaming requests retry from scratch up to 3 times (`allow_retry`), so a failed stage does not poison the result.
- Streaming requests can restart only before any token has been emitted; otherwise the SSE stream emits an error. This is an honest constraint: emitted bytes cannot be unsent.
- If only one healthy node remains, the pipeline runs all layers on it and reports `distributed: false`.

### 4.4 Correctness gate

Tests compare greedy distributed generation byte-for-byte with monolithic `GPT.generate` on the same checkpoint, including KV-cached decode. This catches layer-slice, position, cache and sampling errors.

## 5. Device selection

`auto`:

- CUDA → `cuda:0`
- ROCm build → GPU
- Intel XPU → XPU
- Apple MPS:
  - parameter count ≥ `mps_cpu_threshold_params` (default 50M) → MPS
  - otherwise CPU, because tiny transformer kernels are dispatch-bound on Metal; measured local inference was ~50× slower on MPS for the 0.9M demo model
- otherwise CPU

Explicit `--backend mps|cuda|cpu|...` always wins. Unavailable explicit backends raise instead of silently pretending. `xdc doctor` lists each backend with the reason it is unavailable.

Training and inference are serialized per worker by a compute lock. This is intentional resource isolation, not a performance bug; a worker does not oversubscribe its GPU.

## 6. Scheduling and resource pooling

- Capabilities include CPU model/cores, total/available RAM, GPU memory, platform, PyTorch version and measured matmul GFLOPS.
- Scheduler score = compute GFLOPS × reputation × memory-availability factor.
- Training selects up to `max_workers`; inference selects up to `n_layer` stages and `max_stages`.
- A node that misses heartbeats is marked offline; a node with invalid updates loses reputation and may be banned.
- This is resource pooling, not a general-purpose cluster OS: one training assignment at a time per worker, no arbitrary containers, no preemption.

## 7. C++ core

Optional pybind11 extension compiled from `native/xdc_native.cpp`:

- flat-buffer robust aggregation + outer momentum in C++ (one parallel pass over all parameters),
- deterministic top-k sampling,
- native byte batches,
- int8 block quantizer (not enabled on the wire by default).

The package installs and runs without it. `xdc.native.AVAILABLE` and `xdc doctor` expose the truth.

## 9. Limit of the current design

- Whole-model DiLoCo transfer is appropriate for small/medium models. Larger models need shard/fragment exchange.
- Pipeline inference has per-token network latency; same-host CPU beats the distributed pipeline for the tiny model, while a real multi-machine deployment gains aggregate memory capacity. Benchmarks state both directions.
- No tensor parallelism, LoRA, or RL trainer in v0.1.
- No Byzantine consensus; two-worker robust aggregation is limited.
- No public-swarm incentives or anonymity.
